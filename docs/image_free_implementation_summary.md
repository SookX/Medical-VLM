# Image-Free Implementation Summary

## 1. Purpose And Scope

This document summarizes the current image-free implementation of the
CXReasonBench stage-gated verification project. The goal of this implementation
is to build and validate the experiment machinery before real chest X-ray image
pixels and the restricted official CXReasonBench case package are available.

The larger research idea is to wrap CXReasonBench Path 1 with a
training-free inference-time controller. A frozen medical VLM generates each
reasoning stage. External gates verify the stage. If a stage fails, only that
stage is regenerated. Previously accepted upstream stages are preserved. This
differs from ordinary sequential generation, self-correction, full-chain
restart, and external-tool-first systems.

The image-free variant does not test whether a model can visually inspect a
chest X-ray. Instead, it tests whether the controller, task routing,
deterministic verification, repair logic, baselines, metrics, logging, oracle
interface, and experiment reports behave correctly. It uses the public
CheXStruct CSV files as structured mock evidence. These CSV files contain
anatomical landmarks, measurements, diagnostic indices, and labels generated by
the CheXStruct pipeline.

The implementation deliberately keeps a clear boundary between what is proven
now and what remains for the image-based benchmark. The current system can
evaluate structured consistency and repair behavior. It cannot yet claim visual
grounding performance, because it does not have real image-to-case execution
against official CXReasonBench examples.

The current image-free implementation supports all 12 CXReasonBench diagnostic
and image-quality tasks:

- `aortic_knob_enlargement`
- `ascending_aorta_enlargement`
- `cardiomegaly`
- `carina_angle`
- `descending_aorta_enlargement`
- `descending_aorta_tortuous`
- `inclusion`
- `inspiration`
- `mediastinal_widening`
- `projection`
- `rotation`
- `trachea_deviation`

The main runnable systems are:

- one-pass / greedy structured baseline
- self-consistency baseline
- local repair
- full-chain restart
- mock oracle local repair
- controlled corruption evaluation
- task coverage reporting
- MedGemma text-only dry run

The image-free implementation is therefore a complete experiment scaffold. It
can run repeatable mock experiments, produce JSONL traces and summaries, compare
repair strategies, and identify which verifier types are currently strong or
weak.

## 2. Repository And Data Layout

The repository now contains both the new gated-reasoning code and references to
the upstream benchmark/data sources.

The official CXReasonBench repository is included as a submodule:

```text
external/CXReasonBench
```

This is used as a reference for upstream Path 1 behavior, prompts, model
interfaces, scoring, and metrics. The gated implementation does not modify the
upstream checkout directly. This follows the original design rule: build a thin
integration layer around CXReasonBench rather than rewriting the benchmark code.

The CheXStruct dataset was cloned locally to:

```text
data/CheXStruct
```

The `data/` directory is intentionally ignored by git, because the dataset clone
should not be committed. CheXStruct provides task-specific CSV files for three
source datasets:

- `nih_cxr14`
- `openi`
- `vindrcxr`

Each source folder contains one CSV per task. The CSVs do not share a single
schema, so the implementation reads raw CSV files per task instead of treating
the Hugging Face dataset as one flat table.

The dataset loader lives in:

```text
cxreason/integrations/chexstruct.py
```

It exposes:

- source dataset names
- task-to-filename mapping
- table discovery
- per-task CSV loading

The loader also handles the dataset's shipped filename typo:

```text
abdomial_xray.csv
```

behind the cleaner alias:

```text
abdominal_xray
```

The implementation code is organized under:

```text
cxreason/
```

The major packages are:

- `controller/`: generic Path 1 control flow, state tracking, repair feedback,
  and dependency audit
- `gates/`: stage-verification gates
- `tasks/`: deterministic task registry and task specifications
- `pipelines/`: helpers that wire task specs to controllers
- `baselines/`: one-pass, self-consistency, and full-restart baselines
- `mock_cases/`: CheXStruct-backed mock case generation
- `evaluation/`: logging, metrics, metadata, and coverage reporting
- `prompting/`: prompt templates
- `generators/`: model-backed generators
- `modeling/`: MedGemma adapter
- `integrations/`: external dataset/benchmark access helpers

The main scripts are under:

```text
scripts/
```

The scripts provide runnable entry points for mock pipelines, corruption
evaluation, baseline comparisons, prompt rendering, task coverage reports,
mock-oracle experiments, and MedGemma smoke/dry runs.

## 3. Core Controller Design

The core controller is intentionally medicine-agnostic. It does not know what
cardiomegaly, carina angle, or projection means. It only knows how to move
through ordered stages:

```text
generate -> verify -> PASS or REPAIR -> continue or retry current stage
```

The local repair controller lives in:

```text
cxreason/controller/controller.py
```

Its main concepts are:

- `StageSpec`: pairs a stage name with a verifier gate
- `StageGenerator`: protocol for anything that can generate a stage output
- `LocalRepairController`: executes stages with bounded retries

The expected Path 1 stages are currently:

```text
stage1_criterion
stage2_anatomy
stage3_measurement
stage4_final
```

For each stage, the local repair controller:

1. calls the generator with the current accepted upstream outputs;
2. passes the generated output and context to that stage's gate;
3. records the output, gate result, and accounting information;
4. accepts the output if the gate passes;
5. creates non-answer-revealing repair feedback if the gate fails;
6. retries only the failed stage while preserving accepted upstream stages;
7. fails the case if the retry budget is exhausted.

The controller state lives in:

```text
cxreason/controller/state.py
```

It tracks:

- `case_id`
- `task`
- all generated outputs per stage
- accepted outputs
- attempts per stage
- gate results per stage
- model calls
- verifier calls
- generated token count
- failed stage
- metadata

The state object is shared across local repair, one-pass, self-consistency, and
full restart. This is important because all systems can be logged and measured
with the same metrics functions.

Repair feedback is created by:

```text
cxreason/controller/repair.py
```

The repair feedback intentionally does not reveal the correct benchmark answer.
It contains:

- the failed stage
- a generic verification failure reason
- the instruction to re-evaluate only that stage
- a warning not to assume or reveal benchmark answers

This directly supports the experimental rule that external verification can
return only `PASS` or `REPAIR`, not the answer.

## 4. Task Router And Task Experts

The system uses a deterministic task router, not a learned mixture-of-experts
model. The routing is:

```text
task name -> TaskSpec -> stage-specific gates
```

The task abstraction lives in:

```text
cxreason/tasks/base.py
```

The task registry lives in:

```text
cxreason/tasks/registry.py
```

Each `TaskSpec` defines:

- task name
- display name
- preferred Stage 1 criterion
- accepted criterion terms
- Stage 2 anatomy fields
- Stage 3 measurement or recognition fields
- final decision field
- numeric fields
- ratio checks
- min/max ratio checks
- Stage 3 extra sanity gates
- Stage 4 final-rule gate
- notes
- verification-level labels

The controller never decides which medical rule applies. The task registry
decides that deterministically based on the task name. This makes the system
auditable, reproducible, and appropriate for a benchmark paper. It also avoids
introducing hidden learned routing behavior that could complicate interpretation.

Each task has a Stage 2 schema based on CheXStruct fields. For example:

```text
cardiomegaly:
  heart_xmin
  heart_xmax
  lung_xmin
  lung_xmax
  viewposition

carina_angle:
  point_1
  point_2
  point_3
  viewposition

rotation:
  medial_end_right_clavicle
  medial_end_left_clavicle
  midline_points
  midline_point_right_clavicle
  midline_point_left_clavicle
  viewposition
```

Stage 3 is either arithmetic-checked or sanity-checked:

- arithmetic checks verify ratios derived from component measurements;
- sanity checks verify plausible value domains when the value cannot yet be
  independently derived.

Stage 4 uses deterministic clinical-rule gates for all 12 tasks. These rules
were inferred from CheXStruct label boundaries and validated locally against the
public rows with zero mismatches in the checked data.

The current verification levels are:

- `criterion_terms` for Stage 1
- `structural` for Stage 2
- `arithmetic` or `sanity` for Stage 3
- `clinical_rule` for Stage 4

This split is important. An arithmetic gate is stronger than a sanity gate. A
sanity gate catches impossible or out-of-domain values, but it does not prove
that the image evidence supports the value. Visual verification remains future
work.

## 5. Gates And Verification Logic

The base gate interface is:

```text
cxreason/gates/base.py
```

Every gate returns a `GateResult`:

```python
GateResult(
    passed: bool,
    score: float | None,
    reason: str | None,
    metadata: dict | None,
)
```

The reusable structured gates live in:

```text
cxreason/gates/structured.py
```

They include:

- `CompositeGate`
- `CriterionTermsGate`
- `RequiredFieldsGate`
- `RatioConsistencyGate`
- `MinMaxRatioConsistencyGate`
- `NumericRangeGate`
- `BinaryFieldsGate`
- `ChoiceFieldGate`
- `BinaryDecisionFieldGate`

These gates check format, field presence, numeric typing, arithmetic consistency,
plausible numeric ranges, binary labels, accepted string choices, and final
decision structure.

The deterministic clinical-rule gates live in:

```text
cxreason/gates/rules.py
```

They include:

- `MeasurementThresholdRuleGate`
- `MeasurementRangeRuleGate`
- `AnyMeasurementThresholdRuleGate`
- `AllBinaryMeasurementsRuleGate`
- `DirectionNotFlatRuleGate`

The cardiomegaly-specific gate is:

```text
cxreason/gates/cardiomegaly.py
```

It includes task-specific logic for:

- accepting CTR as the criterion;
- requiring heart and lung width anatomy;
- checking CTR arithmetic;
- applying view-position-dependent CTR thresholds.

The current Stage 4 rules are documented in:

```text
docs/clinical_rules.md
```

The rules are:

```text
cardiomegaly:
  PA ctr >= 0.495
  AP ctr >= 0.545

mediastinal_widening:
  PA mcr >= 0.245
  AP mcr >= 0.325

aortic_knob_enlargement:
  ratio > 2.495

ascending_aorta_enlargement:
  ratio >= 0.1

descending_aorta_enlargement:
  ratio >= 2.5

descending_aorta_tortuous:
  curvature >= 0.00085

carina_angle:
  angle < 39.5 or angle > 80.5

inspiration:
  rib_position <= 8

rotation:
  ratio < 0.395

projection:
  max(ratio_right, ratio_left) >= 0.3

inclusion:
  all six regional inclusion labels are 1

trachea_deviation:
  direction != "flat"
```

These are development rules derived from CheXStruct. They should be treated as
benchmark-linked scaffolding until official CXReasonBench criteria are plugged
in.

## 6. Mock Cases And Image-Free Data Flow

The image-free system uses CheXStruct rows to create mock Path 1 cases. This is
implemented in:

```text
cxreason/mock_cases/chexstruct.py
```

For a given task, source dataset, and row index, the mock builder:

1. loads the task-specific CheXStruct CSV;
2. selects one row;
3. extracts the task's Stage 2 anatomy fields;
4. extracts the task's Stage 3 measurement fields;
5. builds a Stage 1 criterion output from the task spec;
6. builds a Stage 4 final decision from the CheXStruct label;
7. returns a `CheXStructMockCase`.

The resulting object contains:

```text
case_id
task
source_dataset
stage_outputs
```

The `stage_outputs` dictionary has:

```text
stage1_criterion
stage2_anatomy
stage3_measurement
stage4_final
```

For cardiomegaly, a mock case may contain:

```text
stage1_criterion:
  {"criterion": "cardiothoracic ratio (CTR)"}

stage2_anatomy:
  heart_xmin
  heart_xmax
  lung_xmin
  lung_xmax
  viewposition

stage3_measurement:
  heart_width
  lung_width
  ctr

stage4_final:
  cardiomegaly
  task
  viewposition
  verification_level
```

The corrupting mock generator intentionally returns a wrong first attempt for a
selected stage. It then returns the correct structured output on the next call.
This allows controlled repair experiments without a real VLM.

The corruption modes are:

- Stage 1: wrong criterion text
- Stage 2: missing required anatomy field
- Stage 3: corrupted measurement or ratio
- Stage 4: flipped final decision

The local repair controller should reject the corrupted first attempt, retry
only that stage, accept the repaired output, and continue.

This data flow gives a clean way to test controller behavior:

```text
CheXStruct row
-> mock Path 1 stage outputs
-> intentional corruption
-> gate detects corruption
-> controller retries
-> accepted chain is audited
-> metrics and traces are written
```

## 7. Baselines And Experiment Modes

The implementation now includes four main non-oracle systems.

The one-pass baseline lives in:

```text
cxreason/baselines/one_pass.py
```

It generates each stage once. If any stage fails verification, the case fails.
It performs no repair and no retry. This is the image-free equivalent of a
greedy structured Path 1 baseline.

The self-consistency baseline lives in:

```text
cxreason/baselines/self_consistency.py
```

It samples multiple candidates per stage and accepts the first verified
candidate. In the current mock setup, the first candidate may be corrupted and
the second candidate may be correct, so self-consistency can recover. Later,
with MedGemma, this can become true sampled self-consistency.

The local repair controller lives in:

```text
cxreason/controller/controller.py
```

It retries only the failed stage and preserves accepted upstream stages.

The full-chain restart baseline lives in:

```text
cxreason/baselines/full_restart.py
```

If a stage fails, it discards the current trajectory and restarts from Stage 1.
This baseline is important because it controls for extra generation compute
while testing whether local repair is more efficient than global regeneration.

The task-controller builders live in:

```text
cxreason/pipelines/tasks.py
```

They expose:

- `build_task_controller`
- `build_full_restart_task_controller`
- `build_one_pass_task_controller`
- `build_self_consistency_task_controller`

The configurable mock baseline runner is:

```text
scripts/run_mock_baselines.py
```

It can be run from CLI flags or from YAML:

```powershell
python scripts\run_mock_baselines.py --config configs\mock_baselines.yaml
```

The config file is:

```text
configs/mock_baselines.yaml
```

It defines:

- experiment name
- output directory
- source dataset
- row start
- case count
- retry count
- candidates per stage
- task subset
- corruption modes
- systems to run

The runner writes:

- `attempts.jsonl`
- `runs.jsonl`
- `summary.json`
- `system_summary.json`
- `environment.json`

This creates a repeatable experiment folder suitable for later paper tables.

The dependency audit lives in:

```text
cxreason/controller/dependency_audit.py
```

It replays the accepted final chain against the same task spec after local
repair. It checks that the accepted outputs still satisfy each stage gate with
the appropriate upstream context.

The dependency audit is not a new medical verifier. It is a controller-level
consistency check. It is designed to become an ablation:

```text
with dependency audit
without dependency audit
```

In current mock corruption runs, all completed repaired chains pass the
dependency audit.

## 9. Oracle Interface

The oracle gate lives in:

```text
cxreason/gates/oracle.py
```

The oracle pipeline builder lives in:

```text
cxreason/pipelines/oracle.py
```

The oracle gate is intentionally restricted. It returns:

```text
PASS
REPAIR
```

It does not reveal:

- the correct option
- the correct measurement
- the correct anatomy
- the correct final diagnosis
- the hidden benchmark answer

The interface is:

```text
BenchmarkScorer.is_correct(stage, output, context) -> bool
```

The `OracleGate` wraps that scorer and converts the boolean into a `GateResult`.
The current `MockAnswerScorer` is a development-only scorer. It compares a stage
output against hidden CheXStruct-backed mock answers. Later, this can be
replaced by an official CXReasonBench scorer once the restricted case package is
available.

The mock oracle runner is:

```text
scripts/run_mock_oracle_eval.py
```

Example:

```powershell
python scripts\run_mock_oracle_eval.py --tasks cardiomegaly --count 2 --output-dir outputs\mock_oracle_smoke
```

This tests the upper-bound controller mechanism in the mock environment. It
also confirms that the oracle pathway can reject corrupted stage outputs without
leaking answers into repair feedback or gate metadata.

The current oracle interface is therefore ready for later integration with
official CXReasonBench references.

## 10. Prompt Templates And MedGemma Text-Only Dry Run

The project contains two prompt layers.

The original cardiomegaly-specific prompt builder is:

```text
cxreason/prompting/cardiomegaly.py
```

The newer registry-derived all-task prompt builder is:

```text
cxreason/prompting/tasks.py
```

The all-task prompt builder generates strict JSON instructions from the
`TaskSpec`. For each task and stage, it includes:

- task name
- stage identifier
- exact expected JSON keys
- accepted upstream context
- optional repair feedback
- optional development-only structured context

The prompt builder supports all four stages:

- `stage1_criterion`
- `stage2_anatomy`
- `stage3_measurement`
- `stage4_final`

The prompt renderer is:

```text
scripts/render_task_prompts.py
```

Example:

```powershell
python scripts\render_task_prompts.py --output outputs\task_prompts.json
```

The MedGemma adapter lives in:

```text
cxreason/modeling/medgemma.py
```

It supports:

- image plus text generation
- text-only generation

The generic MedGemma task generator is:

```text
cxreason/generators/medgemma_task.py
```

It can generate structured stages for any registered task, optionally with an
image path. If no image is provided, it uses text-only generation.

The text-only dry-run script is:

```text
scripts/run_medgemma_text_dry_run.py
```

Without `--call-model`, it renders prompts without loading MedGemma:

```powershell
python scripts\run_medgemma_text_dry_run.py --task cardiomegaly --row-index 1
```

With `--call-model`, it actually asks MedGemma to generate stage JSON in
text-only mode:

```powershell
python scripts\run_medgemma_text_dry_run.py --task cardiomegaly --row-index 1 --call-model
```

The text-only mode is not a visual benchmark result. It exists to test:

- JSON compliance
- stage-by-stage prompting
- repair prompt behavior
- model/controller integration

This gives a useful intermediate step before real X-ray images are introduced.

## 11. Current Performance

The current image-free system has been tested with unit tests and smoke
experiments.

The latest full unit test result is:

```text
19 tests passed
```

The configured mock-baseline smoke run used:

```text
configs/mock_baselines.yaml
```

It produced:

```text
runs: 48
completed: 36
detected: 48
false_repairs: 0
```

The 48 runs come from:

```text
4 systems x 3 tasks x 2 corruption modes x 2 rows = 48 runs
```

The systems were:

- one-pass
- self-consistency
- local repair
- full restart

The corruption modes were:

- Stage 3
- Stage 4

The one-pass baseline fails intentionally corrupted stages because it has no
retry mechanism. The other three systems recover. Therefore:

```text
3 successful systems x 3 tasks x 2 modes x 2 rows = 36 completed runs
```

This is expected and indicates that the baseline separation is working.

The local repair versus full restart smoke comparison showed:

```text
Stage 3 failure:
  local repair mean calls: 5
  full restart mean calls: 7

Stage 4 failure:
  local repair mean calls: 5
  full restart mean calls: 8
```

Both systems completed the repaired cases, but local repair used fewer calls
because it preserved accepted upstream stages. Full restart regenerated earlier
accepted outputs after a later-stage failure.

The all-task corruption evaluation after Stage 3 sanity gates and Stage 4
clinical-rule gates showed:

```text
120 runs
96 corrupted runs detected
24 clean runs not falsely rejected
120/120 completed
120/120 dependency audits passed
0 false repairs
```

Grouped by mode, the behavior is:

```text
clean:
  no false repairs

stage1:
  criterion corruptions detected

stage2:
  missing anatomy corruptions detected

stage3:
  arithmetic and sanity corruptions detected

stage4:
  clinical-rule corruptions detected
```

This result means the image-free implementation is behaving correctly for
controlled corruption tests.

## 12. What The Image-Free Variant Proves

The image-free variant demonstrates that the project's experimental machinery
works before image pixels are involved.

It proves that:

- all 12 tasks are routed deterministically;
- each task has a Stage 2 anatomy schema;
- each task has a Stage 3 verifier level;
- each task has a Stage 4 deterministic clinical-rule gate;
- local repair preserves accepted upstream stages;
- full restart regenerates upstream stages and uses more calls;
- one-pass fails under intentional corruption;
- self-consistency can recover in the mock candidate setting;
- mock oracle verification can return only PASS/REPAIR;
- corruption evaluation produces interpretable metrics;
- JSONL traces capture every attempt;
- dependency audits replay accepted chains;
- run metadata is saved for reproducibility;
- all-task prompts can be rendered from the registry;
- MedGemma can be connected in text-only dry-run mode.

This is enough to support early mechanism claims in a mock setting:

```text
Local repair can recover from stage-local structured errors while preserving
accepted upstream reasoning states and using fewer generation calls than
full-chain restart.
```

It also gives a foundation for future experiments:

- greedy versus repair;
- repair versus full restart;
- repair versus self-consistency;
- practical verifier versus oracle verifier;
- with versus without dependency audit;
- context-isolated versus full-context verification.

## 13. What The Image-Free Variant Does Not Prove

The current implementation does not prove visual reasoning performance.

It does not show that MedGemma can:

- detect the required anatomical structures in a real chest X-ray;
- estimate landmarks from pixels;
- measure distances from image evidence;
- determine clinical findings from visual evidence;
- reproduce official CXReasonBench Path 1 performance;
- improve final benchmark results.

It also does not yet include:

- real image-to-row pairing;
- official CXReasonBench case JSON loading;
- official Path 1 prompt reproduction;
- official scoring integration;
- patient-disjoint train/development/test split handling;
- independent segmentation-based verification;
- threshold calibration protocol for final evaluation.

CheXStruct is benchmark-linked. It is useful for development and mock
verification, but it should not be described as an independent visual verifier.

The Stage 3 sanity gates are especially limited. They catch impossible values,
such as an angle outside `[0, 180]` or a ratio outside `[0, 1]`, but they cannot
tell whether a plausible value is visually correct. For example, a carina angle
of `70` degrees is plausible, but without image evidence or oracle reference it
cannot be independently verified.

This distinction is important for the paper. The current image-free result is a
controller-and-verifier validation, not a medical VLM benchmark result.

## 14. Next Step Toward Image-Based Experiments

The next transition is to add real image pixels and connect them to task rows.
The easiest path is likely:

1. download one public image source such as NIH ChestX-ray14 or OpenI;
2. build an `image_file -> local image path` resolver;
3. select a small cardiomegaly subset first;
4. run MedGemma with real image plus Stage 1 prompt;
5. parse structured JSON;
6. verify using the current gates;
7. expand to all stages for cardiomegaly;
8. compare one-pass, self-consistency, local repair, and full restart;
9. only then expand to more tasks.

The official CXReasonBench integration should be a separate later layer:

```text
official Path 1 case loader
official prompt adapter
official oracle scorer
official metric reproduction
```

The current implementation already has the right extension points:

- task registry for task-specific schemas and gates;
- generator protocol for MedGemma or other VLMs;
- oracle gate interface for official scorer integration;
- JSONL trace logging for experiments;
- metric summaries for paper tables;
- dependency audit for ablations.

In short, the image-free implementation is complete as a scaffold. It is ready
to support the first image-based pilot once a real image source and image-row
pairing are available.
